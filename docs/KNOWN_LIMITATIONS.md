# Известные ограничения и архитектурные допущения (KNOWN_LIMITATIONS.md)

В данном документе зафиксированы осознанные архитектурные ограничения текущей версии продукта (v1.0 Pilot), а также векторы их развития в следующих релизах.

---

## 1. Архитектурные ограничения v1.0

### 1.1. Однопоточный детейлинг-бокс (Single Bay Assumption)
- **Текущее поведение**: В текущей архитектуре расчёт свободных слотов исходит из модели «1 автомобиль в боксе одновременно». Если на 14:00–16:00 есть подтверждённая или удерживаемая бронь, этот интервал блокируется целиком для всей студии.
- **Обоснование**: Большинство премиальных детейлинг-студий на начальном этапе работают с одним главным постом (или одним мастером по полировке/керамике), где параллельная запись в один бокс недопустима во избежание очередей и срыва сроков.
- **Вектор развития (v1.1+)**: Добавление таблицы `bays` (посты/боксы) и поля `capacity` у компаний с распределением записей по отдельным постам.

### 1.2. Ограничение срока удержания (30-Minute Hold Window)
- **Текущее поведение**: Созданная клиентом запись в статусе `pending` блокирует слот ровно на 30 минут. По истечении 30 минут (или при ручной очистке через cron/RPC) слот снова становится доступным другим клиентам.
- **Обоснование**: Предотвращает умышленную или случайную блокировку расписания пользователями, которые нажали кнопку, но не завершили общение в WhatsApp.

### 1.3. Привязка к WhatsApp
- **Текущее поведение**: Окончательное согласование деталей, осмотра и передачи автомобиля происходит через WhatsApp. Система не принимает онлайн-эквайринг (Kaspi Pay / Stripe) напрямую в интерфейсе, а передаёт предзаполненную заявку в WhatsApp владельца.
- **Обоснование**: В сегменте детейлинга (Казахстан/СНГ) 95%+ коммуникаций и согласование степени повреждения ЛКП традиционно происходят по фото/видео в WhatsApp.
- **Вектор развития**: Интеграция с Kaspi Pay QR / Kaspi Kassa для приёма предоплаты за бронирование.

### 1.4. Хранение изображений портфолио (Client-side Canvas Compression & Data URLs)
- **Текущее поведение**: В миграциях 001–008 бакеты `storage.buckets` Supabase Storage намеренно не инициализируются в PostgreSQL. При загрузке фото в портфолио браузер выполняет сжатие изображения на клиенте через HTML Canvas (`max 1600px`, `quality 0.85`, размер ~200–400 КБ) и сохраняет Data URL (Base64) непосредственно в текстовое поле `gallery_photos.image_url`.
- **Обоснование**: Идеально для первого пилотного клиента (до 15–20 фотографий работ). Устраняет зависимость от внешнего S3/Storage провайдера, сетевые сбои авторизации в Storage API и необходимость настройки сложных RLS-политик на `storage.objects` во время пилота.
- **Вектор развития (v1.1+)**: При расширении каталога свыше 50+ фото рекомендуется настроить публичный Supabase Storage bucket `detailing-gallery` и сохранять CDN-ссылки на объекты во избежание роста объёма базы PostgreSQL.

### 1.5. Локальный Fallback (Offline Store / Fail-Closed в Production)
- **Текущее поведение**: В тестовом и dev-окружении при отсутствии соединения с Supabase приложение может использовать localStorage-эмуляцию. Однако в Production (`import.meta.env.PROD = true`) функция `isLocalModeAllowed()` безусловно возвращает `false` (Fail-Closed архитектура). Если соединение с Supabase недоступно, приложение выдаёт честную ошибку сети, не допуская создания «фантомных» локальных записей, о которых не узнает студия.
- **Обоснование**: Бронирование времени требует строгой гарантии отсутствия овербукинга (No-Overbooking Guarantee), что возможно только при централизованной проверке в единой базе данных.

### 1.6. Web Push Серверная Инфраструктура
- **Текущее поведение**: Базовый Service Worker (`sw.ts`) содержит готовый обработчик `push` и `notificationclick`, а клиент умеет запрашивать разрешение на уведомления. Однако отправка Push-сообщений требует фонового сервиса или Supabase Edge Function с приватным VAPID-ключом для отправки payload через FCM/Apple Push Notification Service. В пилотной версии основным каналом мгновенных уведомлений является WhatsApp.
- **Вектор развития**: Развёртывание Supabase Edge Function `send-push` с `web-push` библиотекой и VAPID-парой ключей.

| Платформа | Браузер | Статус | Примечание |

## 3. Мониторинг и метрики пилота
- Время ответа RPC `get_available_slots`: < 80 мс;
- Время создания брони `create_booking`: < 120 мс;
- Ошибки дублирования слотов (Double Bookings): 0%;
- Ошибки потерянных ответов (Lost Response errors): 0% (устранено через `idempotency_key`).
