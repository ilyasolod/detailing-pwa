# Контрольный список безопасности перед Production (SECURITY_CHECKLIST.md)

**Дата ревизии:** 1 ноября 2026 г.  
**Статус проверки:** Локальный аудит пройден (12/12 проверок успешны).

Этот документ содержит обязательный чек-лист безопасности для развёртывания мультитенантной PWA детейлинг-центров в продакшен-окружении Supabase и облачного хостинга.

---

## 1. Мультитенантность и изоляция данных

- [x] **Изоляция административных RPC:**
  - Все административные RPC-функции (`get_owner_dashboard_data`, `save_service`, `delete_service`, `update_company_schedule`, `update_company_settings`, `create_blocked_interval`, `delete_blocked_interval`, `create_manual_booking`, `reschedule_booking`, `add_portfolio_photo`, `delete_portfolio_photo`) содержат проверку:
    ```sql
    IF NOT is_company_admin(p_company_id) THEN
        RAISE EXCEPTION 'Unauthorized: you are not an administrator of this company';
    END IF;
    ```
  - Проверено: администратор компании А получает ошибку 400 (`Unauthorized`) при любых попытках вызвать RPC для компании Б.
- [x] **Изоляция на уровне строк (RLS):**
  - RLS включён (`ENABLE ROW LEVEL SECURITY`) на всех таблицах базы данных.
  - Таблица `bookings`: не имеет политик для роли `anon`. Анонимные пользователи не могут читать или изменять таблицу напрямую через PostgREST.
  - Таблицы `companies`, `services`, `gallery_photos`, `weekly_schedule`, `schedule_breaks`: глобальный публичный доступ на чтение удалён в миграции `005_tenant_security.sql`. Публичные клиенты получают данные строго через функцию `get_company_by_slug`.
  - Прямой `SELECT` из таблицы `bookings` аутентифицированным администратором ограничен условием `public.is_company_admin(company_id)`. Администратор не видит записей чужих компаний.
- [x] **Изоляция привязки услуг (Cross-tenant services check):**
  - При создании бронирования (`create_booking`) проверяется условие:
    ```sql
    WHERE company_id = p_company_id AND id = ANY(p_service_ids) AND active = true
    ```
  - Невозможно заказать услуги одной студии через профиль другой студии.

## 2. Безопасность SQL и RPC-функций

- [x] **Фиксированный `search_path`:**
  - Все `SECURITY DEFINER` функции имеют директиву `SET search_path = public`.
  - Исключена уязвимость подмены схемы (search_path hijacking) злоумышленником.
- [x] **Защита от SQL-инъекций:**
  - Используется строго параметризованный ввод в PL/pgSQL без динамического формирования SQL через конкатенацию строк (`EXECUTE '...' || ...` отсутствует во всех функциях приложения).
  - Проверено: передача `' OR '1'='1` в `get_company_by_slug` воспринимается как литеральная строка и возвращает `null` (честный 404).
- [x] **Валидация типов данных и UUID:**
  - Некорректные или вредоносные строковые идентификаторы на месте UUID перехватываются парсером PostgreSQL и возвращают контролируемый статус 400.
- [x] **Транзакционные блокировки от гонок (Race Conditions):**
  - Функция `create_booking` начинает транзакцию с взятия транзакционной блокировки `pg_advisory_xact_lock(hashtext(p_company_id::text))`.
  - Конкурентные запросы внутри одной компании обрабатываются строго последовательно.

## 3. Идемпотентность и целостность бронирований

- [x] **Уникальный ключ идемпотентности (`idempotency_key UUID`):**
  - В таблице `bookings` колонка `idempotency_key uuid` снабжена уникальным индексом:
    ```sql
    CREATE UNIQUE INDEX uq_bookings_company_idempotency
    ON public.bookings (company_id, idempotency_key)
    WHERE idempotency_key IS NOT NULL;
    ```
  - В таблице `booking_idempotency_records` фиксируется хэш входящих параметров (SHA-256) и точный payload ответа.
  - Повтор с тем же ключом и теми же параметрами возвращает исходную бронь без дублирования в БД.
  - Повтор с тем же ключом, но изменёнными параметрами отсекается ошибкой.

## 4. Аутентификация и сессии

- [x] **Разделение авторизации по арендаторам:**
  - Фронтенд-страница `/c/:slug/admin` сопоставляет пользователя с `company_admins` для целевой компании.
  - Если пользователь авторизован в компании А, но переходит по адресу компании Б, отображается форма входа в компанию Б.
  - Предотвращено отображение дашборда чужой студии во время переключения маршрутов (`isTransitioning` guard).
- [x] **Безопасный выход (`logoutOwner`):**
  - Синхронно очищает локальные данные сессии (`STORE_AUTH_KEY`).
  - Вызывает `supabase.auth.signOut()` для инвалидации токена.
- [x] **Истечение срока сессии:**
  - `validateOwnerSession` проверяет поле `expires_at` токена и производит онлайн-проверку прав в `company_admins`. При отзыве прав доступ мгновенно прекращается.

## 5. Файловое хранилище (Storage)

- [x] **Ограничение размера файлов:**
  - Клиентский лимит — не более 15 МБ на изображение.
- [x] **Проверка типов файлов (MIME Types):**
  - Разрешены только изображения (`file.type.startsWith('image/')`: JPEG, PNG, WebP).
  - Исполняемые файлы (`.exe`, `.sh`, `.php`, `.html`, `.svg` со скриптами) отклоняются до передачи в хранилище.
- [x] **Санитизация имён файлов:**
  - Имена очищаются от небезопасных символов (`file.name.replace(/[^a-zA-Z0-9.-]/g, '_')`).
- [x] **Структура путей в Storage:**
  - Файлы сохраняются в изолированные директории: `companies/${companyId}/${folder}/${timestamp}_${fileName}`.

## 6. Конфигурация окружения (Environment & Secrets)

- [x] `SUPABASE_SERVICE_ROLE_KEY` **НИКОГДА** не включается во фронтенд-бандл и не передаётся в клиентский код Vite (`import.meta.env`).
- [x] На клиенте используется только публичный `VITE_SUPABASE_ANON_KEY`.
- [x] В продакшен-сборках демо-авторизация и fallback на localStorage принудительно отключены (`isLocalModeAllowed() === false`).
- [x] Защита от перехвата: в продакшене обязательно наличие HTTPS и валидного SSL-сертификата.
